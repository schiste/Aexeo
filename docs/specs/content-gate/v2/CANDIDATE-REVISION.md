# Experimental candidate revision profile

This profile connects `CandidateSnapshot` to the [revision-set identity](REVISION-SET.md). `content-impact` emits `candidate_revision_sha256` when this encoding succeeds, including when its link impact is `not_checked`. The hash identifies exactly the supplied representation; it is not a verdict, proof of a complete inventory or accurate links, source authority, freshness, publication authorization, or protection against a publication race. The host is responsible for those boundaries. This profile represents only the fields below: a complete decision must separately bind change semantics, metadata, policy, evaluator, options and all other relevant inputs.

For each string, encode its UTF-8 bytes with an unsigned big-endian `u64` byte length. Encode optional strings as byte `0` for absent or byte `1` followed by the string encoding for present, even if empty. No Unicode normalization is performed.

The `scope` byte string for the revision-set algorithm is ASCII `content-gate:candidate-scope:v1` and a zero byte, followed by encoded `scope`, `site_id`, and optional `site_base_url`.

The `snapshot` byte string is ASCII `content-gate:candidate-snapshot:v1` and a zero byte, followed by the encoded base kind (`git` or `opaque`), encoded base revision, and one byte `0` or `1` for the host's inventory completeness assertion. The base is the pre-change revision, not a published candidate revision.

Each record ID is the exact UTF-8 `entity_id`. Its record bytes are ASCII `content-gate:candidate-item:v1` and a zero byte, followed in order by encoded `public_path`, `media_type`, optional `revision`, encoded `sha256`, and encoded `source`. The links field is one byte `0` if unobserved, or byte `1`, an unsigned big-endian `u32` count and each encoded link in supplied order. Therefore absent links and an observed empty list are distinct; changing link order changes the identity. Record order is normalized by the enclosing revision-set algorithm, which rejects duplicate IDs. All fields, including the host's completeness assertion, are bound, but their validity is independently checked by the overlay, not established by hashing.

The enclosing algorithm's resource limits apply, including a maximum of 100,000 records and 64 MiB of encoded scope, snapshot, IDs and records. Hashing can therefore reject an otherwise representable input if framing pushes it over the limit; the CLI reports `not_checked` in that case. The shared JSON fixture has UTF-8 inputs; Rust and Python independently implement the byte framing. A future interoperable publication protocol must specify all decision artifacts, independently validate their provenance and completeness, and revalidate at a protected publication boundary.
